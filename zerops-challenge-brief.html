01

The verdictLead with this · everything else is support

Ephemeral full-stack environments for AI-generated pull requests

“Every AI-written pull request gets a real, running, throwaway production stack — because you can't review what you can't run.”

A GitHub App. On PR open, it calls the Zerops REST API to create a new isolated project — app service + Postgres + Valkey — runs migrations, seeds representative data, and comments the live URL on the PR with a resource and cost readout. On merge, close, or TTL expiry it destroys the project. A reconciler sweeps orphans so nothing leaks.

Why it wins on the stated rubric

  1. Zerops is load-bearing, not decorative. The product cannot exist without API-driven provisioning of isolated, stateful, networked projects. Vercel and Netlify previews give you a frontend against one shared database — so two PRs touching the schema collide. This gives each PR its own network, its own Postgres, its own state.
  2. The problem is 2026-shaped and real. Coding agents now open PRs faster than humans can review them.
  3. The demo is one unbroken 60 seconds. Agent opens PR → bot comments “environment ready” → click → working app with seeded data → merge → environment gone.
The beat that closes the argument

Mid-demo, show a second PR running simultaneously with a conflicting schema change — both green. That is the entire case against shared-database previews, in five seconds. Do not skip it.

Runner-up for pure spectacle: the Resilience Drill — kill the Postgres primary live, app stays up. Wildcard for memorability: per-match UDP game servers.

03

What actually winsPublished rubrics · named winners · a judge's own account

The published criteria

WeMakeDevs reuse six dimensions across their events: Potential Impact · Creativity & Originality · Technical Implementation · Learning & Growth · Aesthetics & UX · Presentation & Communication.

Note that Learning & Growth and Presentation are a third of the rubric. That is unusually generous to a well-told story — which means the demo video and README are scored artifacts, not packaging.

What moves scores in practice

Everyone lands mid-range on the published rubric. The spread that produces a winner comes from two or three things the rubric does not name. Working hackathon judge · DEV · July 2026
#DifferentiatorFinding
1Whether the demo ran“The single largest score differentiator I saw. A working demo, live, beats a more ambitious project shown as slides almost every time — because a live demo removes doubt, and doubt is what a judge is actually managing under time pressure.”
2Whether you said what it is in sentence oneTeams opening with context or market size lost a third of the slot before the judge knew what they were looking at. Give the anchor first.
3Whether scope matched the time“One narrow thing built well reads as a team that made decisions. A platform in 36 hours reads as a team that did not.”
4Admitting a limitation counterintuitive“Teams that say nothing breaks lose credibility instantly, and teams that name the weakness gain more than they lose.”
5A one-line identity“Judges score partly on whether they can imagine explaining your project to someone else.” Three features with no center don't survive discussion.

What explicitly does not move scores: framework choice, credentials, slide decks, and polish beyond legibility — “elaborate UI does not add on top of legible UI, and past a point it makes me wonder where the backend time went.”

Sponsor-tech depth is the multiplier

An analysis of 8,200 ETHGlobal projects across 38 events found that when a hungry specialist sponsor meets a genuinely novel category, projects win at 3.30× expected rate. But:

Alpha is a window, not a level. It closes on saturation every single time.

One themed event drew 217 near-identical clones fighting over ~36 prizes; those projects won at well under half expected rate. Zerops is exactly the hungry specialist sponsor. The 3.3× is available — but only if your project isn't the thing forty other people also built. Which is what §05 is for.

The AI-disclosure play

Every 2026 rulebook surveyed converges on the same line: disclosure is free, non-comprehension is fatal. One states outright that “using AI tools with proper disclosure does not disadvantage your submission.” The disqualifiers are undisclosed use, hallucinated logic, spray-and-pray submissions, and submitting output you never ran or understood. “If a judge asks explain this code, you must be able to.”

Turn compliance into a scoring signal

Ship an AI-USAGE.md naming exactly what each tool did — e.g. “Claude Code for the Zerops API client and the teardown reconciler; hand-written: the provisioning state machine and webhook verification.” Then be able to explain the state machine cold. Given differentiator #4 above, volunteering your own limits raises your score.

The seven capabilities that are genuinely hard to get elsewhere

#CapabilityWhy it's an unlock
1Public REST API + published OpenAPI spec + Go SDKYou can create and destroy entire projects and services programmatically. This is the foundation for anything ephemeral — preview envs, sandboxes, per-tenant stacks, match servers. Very few PaaS expose this.
2Raw TCP and UDP ports
run.ports[].protocol		Inbound SMTP, MQTT, DNS, QUIC, game protocols, WireGuard. Structurally impossible on Vercel, Netlify or Workers. Almost nobody builds here.
3One-click HA — 3-container clusters as a toggleReal failover you can demonstrate. Competitors gate this behind enterprise tiers.
4Full Linux + Docker service type, rootArbitrary or untrusted workloads, custom daemons, anything needing apt install.
5WireGuard VPN into the project network
zcli vpn up		Your laptop joins the private network; local code talks to db:5432 directly. Genuinely great demo material.
6crontab + startCommands in zerops.ymlScheduled jobs and multi-process containers with no external scheduler.
7Autoscaling, and no scale-to-zeroVertical re-evaluated ~every 10s in 0.125 GB steps; horizontal 1–10 containers. The absence of scale-to-zero is a feature: long-running processes, websockets and stateful daemons just work, no cold starts.

ZCP — the sponsor's own MCP server for coding agents

Confirmed real and active. zeropsio/zcp, pushed 05 Aug 2026, docs live, announced public preview May 2026. Runs remotely as a zcp@1 service inside your project or locally over zcli vpn up. Supports Claude Code, Codex, Antigravity, Grok Build. Exposes deploy, logs, events, env, scale and verify operations.

This cuts both ways — plan around it

Don't build “an MCP server so agents can deploy to Zerops.” The sponsor shipped it three months ago; you'd be demoing their own product back to them.

Do use it as a disclosed accelerator, and do build agent-facing infrastructure on Zerops.

Pricing reality for a weekend

Lightweight project core is free; Serious is $10/mo. Shared CPU $0.60/core/mo, dedicated $6.00, RAM $3.00/GB/mo, disk $0.10/GB/mo — all billed per minute. With a $65 trial credit, a weekend of spinning projects up and down costs cents. Provisioning-heavy ideas are financially safe.

02

Resilience Drill — chaos testing that proves your HA

“Push a button, kill your database primary, and get a report proving your app survived.”

best spectacle Zerops load-bearing ×2 feasibility: high risk: reads as demo-ware

Point it at a Zerops project. It runs a scripted drill via the API — kill the Postgres primary, kill an app container, saturate a service — while continuously probing your endpoint. Output: a timeline of failover duration, dropped requests and recovery, as a shareable report you can run in CI.

Why Zerops is load-bearing: real 3-node HA is a toggle here and an enterprise tier everywhere else. You cannot demonstrate genuine Postgres failover on Render's hobby tier at all. The project's entire value derives from the sponsor's most differentiated feature — the most direct possible answer to “how is Zerops used.”

Verify in hour 0
That you can kill a specific HA replica via the API. If not, the idea collapses.
Framing that saves it
Call it resilience CI, not a chaos toy.
Limitation to volunteer
“Three fault types only, and I measure from outside the cluster — so my failover numbers are upper bounds.”
Why not #1
Killing a live database on camera is the most memorable 10 seconds of the weekend — but the product story is thinner, and judges reward something they can explain as a thing people would use.
03

Email-as-an-API — inbound SMTP

“Give any app a real email address that turns inbound mail into structured webhooks — on your own infra.”

sharpest differentiation uniquely enabled feasibility: medium risk: port 25 blocked?

A real SMTP server on a raw TCP port, parsing inbound mail into structured JSON (sender, subject, body, attachments → object storage), stored in Postgres, delivered as signed webhooks, with a live inbox UI. Self-hostable Postmark-inbound.

Why Zerops is load-bearing: the strongest “impossible elsewhere” story in this brief. You cannot bind an inbound SMTP port on Vercel, Netlify or Cloudflare Workers. It needs a raw TCP listener, a long-running process, persistent storage and no scale-to-zero — exactly the shape Zerops has and serverless platforms don't.

Verify first thing
That Zerops routes external traffic to your inbound port and that 25 isn't blocked.
Fallback
Port 2525 + documented relay — or pivot to MQTT ingest → ClickHouse (same architectural story, no port politics).
Don't hand-roll
Use emersion/go-smtp or aiosmtpd. Never write a MIME parser at a hackathon.
Limitation to volunteer
“No SPF/DKIM/DMARC verification, and I'm on a non-standard port — this is a receiver, not a deliverability story.”
04

Dedicated UDP match servers, provisioned per game

“Every match gets its own authoritative game server, spun up on demand and destroyed when the match ends.”

most memorable uniquely enabled feasibility: low–medium risk: scope

A browser game whose matchmaking service provisions a real dedicated authoritative server on a raw UDP port via the Zerops API, hands both clients the endpoint, and destroys it when the match ends.

Why Zerops is load-bearing: UDP + API-driven provisioning + no cold starts. Unavailable on essentially every mainstream PaaS. The Minecraft and Quake 3 recipes prove UDP game workloads run — but those are “run a server” recipes, not “provision a server per match” products, so you aren't duplicating them.

Only attempt if
You already have game and netcode reflexes.
Mitigation
Make the game trivially simple — two dots and a ball. The product is the provisioning, not the gameplay.
Failure mode
Two of {game, netcode, provisioning} eat the whole weekend.

The Social TrackA separate prize · cheap relative to the MacBook

Post anatomy

  1. Line 1–2 is everything. A specific claim or number plus a surprise. Never “excited to announce.”
  2. Native video in the first post. External links are deprioritized ~40–60%; native video outperforms link posts 3–5×. Put the live URL in a reply and say “link in replies.”
  3. Tag @zeropsio first, @WeMakeDevs second. The first tag reliably triggers the notification that gets you reposted.
  4. One specific Zerops sentence, not gratitude. “Each PR gets its own Postgres because Zerops lets me create whole projects over an API” gets quoted. “Thanks for the platform” does not.
  5. Then a 5–8 post thread on the build: the thing that broke, the fix, the number. Single post or thread — no middle length.
  6. Answer every reply for the first 30 minutes. Replies weigh more than likes; ~20 replies in 30 minutes is the “For You” trigger.

1. A dead live URL at judging time.  2. A demo video where the terminal is unreadable.  3. A README that explains your architecture before it says what the thing is.
